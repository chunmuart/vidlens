# 100条视频之后，怎样测出Agent改进是否有效

这是开始采集时的实验设计，保留作为历史方案。2026-11-16已完成837题检索、60题规划/分配/验证/补检索、12题答案对照，实际协议与结果见[当前成果](../agent_video100_v2/RESULTS.md)。下文尚未执行等措辞描述当时状态，不应覆盖当前成果；追问、人工视频金标、提取精度、并发恢复等仍未完成。
原始素材与证据在`.runtime/evals/video_pool_100_v1/`；实际完成数以`inventory.json`为准。
首批15视频/274机器银标题的检索实验已经完成，见`../real_bilibili_v1/RESULTS.md`。

## 先确定要证明的事

最值得围绕项目讲的三个问题是：复杂问题有没有漏问、有限上下文有没有漏掉后面的子问题、缺证据时能不能有针对性地补回来。
验证和最终回答的评测负责确认这些操作确实提高可信度，并检查多花了多少时间和Token。
不需要每一步都发明一个算法，也不需要每个指标都上涨。失败的实验要保留。

## 规划具体怎么打分

例题：“讲了哪两种检索方式？各自有什么限制？最后为什么选混合？”先由人按用户意图列参考目标，不能让Planner看到答案或参考目标。

审核人把每个实际子问题与参考目标做语义对应，允许合理合并，不能只看文字重合。拆成十条不意味着覆盖十分；重复目标只算一次。

- 必需目标Recall = 被实际计划覆盖的必需目标数 / 必需目标总数。
- 规划Precision = 有效且属于用户需求的实际目标数 / 所有实际目标数；重复、无关、擅自增加的目标要扣分。
- 整题无遗漏率 = 所有必需目标都覆盖的题数 / 题数。
- 同时报告额外目标、重复目标和规划失败。目标层F1要先统一“原子目标”的粒度，不能把一条合理合并的子问题直接判成漏项。

当前`_plan_node`只看用户问题。这一阶段测需求理解，不要求它提前知道视频里的答案。用户问的目标在视频中无答案，Planner仍应保留这个目标，交给检索和验证判断缺失。
已有`evaluate_suite.py planning`能导出整题人工审查表，但尚无细粒度目标对应评分；需要补原子目标标注与审核映射。

## 证据分配是最适合先做的Agent对照

当前`_collect_candidates`先搜各槽候选，`_assemble_ledger`在18条上限内轮流选直接证据，最后补相邻片段。
比较时缓存同一份规划、direct/adjacent候选和排序，只换选片规则。不要让新方案额外检索更多次，然后把提升全部归因于轮流分配。

优先挑有3个以上独立目标的真实问题；把目标顺序颠倒再复跑，观察末尾目标是否更容易被挤掉。
不能拿“每槽至少有一条相关片段”当成功；那一条必须实际支持这个槽需要的事实。
这一阶段用参考目标定位，另跑一遍真实Planner目标定位，区分“规划漏了”和“选证据漏了”。

## Verifier不是让Agent给自己打分

Verifier是被测对象，独立标注才是评分依据。它说“充分”，不代表评分器也应该判充分。
首批可从开发视频挑30个问题，各准备4种账本，形成约120个验证输入，四组分开报结果：

1. 支持完整：事实、主体和数值都齐，应该放行。
2. 缺关键事实：只缺一个必要条件/一侧比较对象，应该指出缺项。
3. 主题相近但对象错误：例如同样的140W，实际属于另一个端口，应该拦截。
4. 数值或否定冲突：账本内证据冲突，应该保留不确定性，不能强行选有利答案。

删一条已标片段不一定真的删干净：同义ASR、OCR或相邻段可能也给出了答案。需要检查整份输入账本。
人工改数字/制造冲突的样本标记为“真实材料派生的受控扰动”，不能叫原视频天然错误案例。
原视频没有答案与“本次账本没搜齐”也必须分开；后者可能被补检索挽救。

以“不充分”为正类：TP=正确拦截不足，FP=把充分误判不足，FN=不足却放行，TN=充分且放行。
拦截Recall=TP/(TP+FN)，误放行率=FN/(TP+FN)，误拒率=FP/(TN+FP)。还要报告样本组成和两类F1，避免全拒答得高分。
超时、异常、缺预测单独计入执行失败，不能冒充“正确拒答”。

## 补检索怎样证明有用

只在第一次证据不足的题里算挽救率，同时报全体题的最终效果；不能事后只选补成功的例子。
三个分支共用首次账本、同一个不足判断、同一证据库、相同总预算；重复原检索与定向检索有相同新增调用额度。
记录修复前后实际支持的目标、缺项、证据ID和新增用量。若前后都充分，不计“挽救成功”。

当前生产返回轨迹主要保留最终账本摘要和最终验证结果，不能据此倒推修复前评分。
离线适配器需在阶段之间保存首次账本/验证、定向查询、最终账本/验证；先加实验记录，再跑对照。不要根据最终`repairCount`自称修复有效。

## 回答、引用、Critic要分开

回答正确率：按独立标准要点核对事实，正确但漏答和说全但夹带错误分别记录。引用支持率：引用是否真的支撑对应主张。引用覆盖率：所有应被支持的主张里有多少附了有效支持。
证据ID存在只说明格式有效，不能证明语义支持；同一个错误答案引用十次不能拿满分。
Critic还可测错误草稿识别：固定同题、同账本的正确草稿与带单个错误的草稿，看它的拦截/误杀；“修改后变长了”不等于修好了。
自动模型可做盲审初筛，需留理由和证据；用独立模型并人工抽查分歧，不能把生产Verifier/Critic的自评分再当标准答案。

## 数据怎么分，后面做多少

100条视频对本项目第一轮足够启动；真正瓶颈是标注质量、题型覆盖和来源独立性，不能仅凭数量保证结论可靠。
先完成100条可用素材，新增85条暂不打检索分，也不自动变成“人工金标”。

- 首批15条已经看过成绩，全部归为探索来源，不能再称最终未见测试视频。
- 新增来源按作者分组，再检查同主题近重复。冻结约60条开发、20条验证、20条最终测试；若作者重叠应调整实际数量，整组不拆，首批15条计入开发。
- 第一轮先人工核对约200–300题，覆盖简单事实、画面参数、多目标、比较/枚举/时序、追问与无答案。按来源分开，不靠同义改写凑题。
- 后续再扩到约800–1000题是工作目标，尚未生成。参考构成：35%事实、15%OCR/数字、25%多目标或多证据、10%时间与顺序、10%追问、5%原视频无答案；视视频内容调整，不强迫每条都凑所有题型。
- 对检索先按“已提取证据里可回答”标注。另设原视频可回答但ASR/OCR漏掉的子集，测端到端瓶颈，别混成检索算法差。
- 规划、验证和补检索可复用同一批视频，但输入/标签不同；120个验证账本不等于120条新视频，也不等于120个独立来源。

终测金标只交给评分器，不进Agent输入；按caseId/BV/作者保存划分清单。先冻结目标指标、模型、Prompt、预算与参数，再跑终测；看过终测后继续调优就要另留新来源。

提取质量先做小而独立的抽样：例如10条不同画面密度/口音视频，每条人工转写30秒并核对2帧，共5分钟音频和20帧。这个数量只是第一轮工作量建议，尚未标注；OCR漏抽到关键画面和抽到了但认错分开统计。不要把检索Recall当ASR/OCR识别精度。高密度文字造成的OCR输出截断也属于运行失败，应保留，不能把失败样本悄悄删掉后声称对所有类型都好。

## 实施顺序与现有入口

先做“检索→证据分配→验证/补检索→最终回答”，规划与追问穿插补标。这样优先验证项目已有的核心改进，不需要增加复杂后台系统。

| 入口 | 已实现 | 还缺什么 |
| --- | --- | --- |
| `compare_retrieval_methods.py` | 五组固定快照检索和向量缓存；首批真实银标已跑 | 人工金标、未见来源终测 |
| `evaluate_suite.py planning/answer` | 整题规划/答案人工表、规则筛查、拒答统计 | 原子目标映射、独立主张与引用语义标注 |
| `run_agent_replay.py` | 固定证据重放当前Agent、轨迹、耗时、usage | 消融分支、每阶段前后快照、验证/修复专用数据适配 |
| `evaluate_real_video.py` | 原视频到最终报告的API入口 | 实际媒体映射、审过的端到端题集与运行 |
| `prepare_video_pool.py` | 独立100视频池、断点产物、失败替补、来源与证据清单 | 题目和人工标签另行准备；收集不是完成评测 |

所有对照保留逐题输出和失败，不只保留总分。不同模型/提示词策略建议至少重复3次，报告均值和波动；比较差异按视频或作者成组重采样，不能把同视频几十道题当完全独立。
Token来自供应商usage，失败用量未知就标未知。单独记录完整处理与固定证据重放耗时，不能把缓存后的检索毫秒数当线上总延迟。

## 简历怎么落笔

现在可写“构建真实视频评测素材池并实现五组检索对照”，具体数量以已完成清单为准。
做完标注与实验后才填：“针对多目标问题证据被挤占的问题，采用逐槽分配，在N视频/M题上使全槽完整率从A提高到B，平均增加C Token。”
其中A/B/C必须来自实际同条件运行；如果没有涨，保留负结果并分析分词、问题措辞和证据噪声，不能倒填数字。
